Destiny 2 PvP データベース設計プラン

Destiny 2 PvP Database Plan

データベース（DATABASE）とバトルログ（BATTLE LOG）を分離し、英語/日本語切替、PvP POTENTIAL、武器使用率、K/U、パーク差分、エキゾチック防具採用率を、低コストで継続公開するための初期設計です。

Initial architecture for a low-cost, bilingual Destiny 2 PvP archive with separate DATABASE and BATTLE LOG layers, PvP Potential, usage, K/U, perk deltas, and exotic armor adoption metrics.

結論

Recommendation

まずはこのフォルダ内で「静的生成サイト + バージョン管理されたテキストデータ」として作り始めます。GitHubはテキストデータとコードの保管に限定し、画像と武器データ参照のコミュニティ基盤は、最終大型アップデート後に新設するDiscordサーバーで整えます。

重要なのは、Bungie APIには「全世界のPvP試合を横断取得する公式firehose」が見当たらない点です。したがってBATTLE LOGは、最初から「観測サンプルに基づく統計」として設計し、対象母集団、取得経路、信頼区間を明示するべきです。

Start inside this folder with a static-generated site and versioned text data. GitHub will be limited to text data and source code, while the community layer for images and weapon-data reference will be built later through a new Discord server after the final major update.

The key constraint is that Bungie does not appear to expose an official global PvP match firehose. Dynamic metrics should therefore be presented as observed-sample statistics, with sample coverage and confidence clearly displayed.

Static first Versioned manifest Bilingual labels Sample-aware PvP stats GitHub text only Discord after final update

DATABASE / BATTLE LOG 分離方針

DATABASE and BATTLE LOG Split

データベース

DATABASE

武器・防具・パーク・ローカライズ・PvP POTENTIALモデルなど、パッチ単位で変わる情報を扱います。Bungie Manifestを土台にし、PvP POTENTIALは別テーブルで手動検証/コミュニティ検証/計算式をバージョン管理します。

Stores items, armor, perks, localization, and PvP Potential models that change by patch. Bungie Manifest is the foundation; PvP Potential is maintained in separate versioned tables with measured data, community references, and formulas.

  • entity: hash、分類、装備スロット、アイコン、レアリティ
  • entity_i18n: hash、language、name、description
  • weapon_static: weaponHash、RPM、frame、ammo、stats、perk pool
  • ttk_profile: sandboxVersion、weapon/archetype、resilienceTier、対象HP、WP、精密/ボディダメージ、Optimal TTK、BS TTK、BS許容
  • sandbox_version: 有効開始日、Manifest version、出典、検証状態
  • entity: hash, category, slot, icon, rarity
  • entity_i18n: hash, language, name, description
  • weapon_static: weapon hash, RPM, frame, ammo type, stats, perk pool
  • ttk_profile: sandbox version, weapon/archetype, resilience tier, target HP, WP, precision/body damage, Optimal TTK, BS TTK, body-shot forgiveness
  • sandbox_version: effective date, manifest version, source, validation status

バトルログ

BATTLE LOG

試合ログ、武器別キル、観測されたロードアウト、日次/週次集計を扱います。PGCRには武器別キルはありますが、武器ロールのソケット/パークはそのまま入らないため、パーク差分には装備スナップショット設計が必要です。

Stores match logs, weapon kills, observed loadouts, and daily/weekly aggregates. PGCR includes weapon-level kill stats, but not full roll sockets/perks, so perk-delta analysis requires a loadout snapshot strategy.

  • match: activityId、mode、map、period、manifestVersion
  • match_player: activityId、匿名playerKey、class、team、result、scoreboard stats
  • match_weapon: activityId、playerKey、weaponHash、kills、precision、使用区分
  • loadout_snapshot: playerKey、characterId、取得時刻、武器/防具itemHash
  • perk_snapshot: itemInstanceIdHash、weaponHash、plugHash、slotIndex
  • agg_weapon_daily: mode、date、weaponHash、usage、killShare、K/U
  • agg_exotic_armor_daily: mode、class、exoticArmorHash、adoptionRate、winRate proxy
  • match: activity ID, mode, map, period, manifest version
  • match_player: activity ID, anonymized player key, class, team, result, scoreboard stats
  • match_weapon: activity ID, player key, weapon hash, kills, precision, usage flag
  • loadout_snapshot: player key, character ID, timestamp, equipped weapon/armor hashes
  • perk_snapshot: item instance hash, weapon hash, plug hash, slot index
  • agg_weapon_daily: mode, date, weapon hash, usage, kill share, K/U
  • agg_exotic_armor_daily: mode, class, exotic armor hash, adoption rate, win-rate proxy
PvP POTENTIALはBungie Manifestだけで完全自動生成できる情報ではありません。RPMや武器定義は取れますが、PvPダメージ値、バースト間隔、ダメージ減衰、パーク補正、耐久Tierごとの閾値は、パッチノートと検証データを組み合わせる前提で設計します。
PvP Potential cannot be fully generated from the Bungie Manifest alone. RPM and item definitions are available, but PvP damage values, burst timing, falloff, perk modifiers, and resilience breakpoints should be managed from patch notes plus verified test data.

データ取得パイプライン

Data Pipeline

Manifest同期。 /Destiny2/Manifest/ でversionを確認し、英語と日本語の定義を取得。hashを主キーにして差分を保存。
観測対象の収集。 opt-inプレイヤー、クラン、コミュニティ協力者、公開プロフィール許可ユーザーからキャラクターとActivity Historyを取得。
PGCR取得。 activityIdでPost Game Carnage Reportを取得し、プレイヤー、武器別キル、試合結果、モード、マップを正規化。
ロードアウトスナップショット。 試合履歴取得直後にCharacterEquipmentとItemSocketsを取得。タイミングずれを記録し、信頼度を付与。
集計と公開。 生ログは非公開/圧縮保管、公開サイトには日次/週次の集計JSONと小さな検索インデックスだけを出す。
Manifest sync. Check /Destiny2/Manifest/, download English and Japanese definitions, and store diffs by hash.
Observed population. Use opt-in players, clans, community contributors, and public profiles that allow access.
PGCR ingestion. Fetch Post Game Carnage Reports by activity ID and normalize players, weapon kills, outcomes, mode, and map.
Loadout snapshots. Fetch CharacterEquipment and ItemSockets immediately after activity discovery. Store timing lag and confidence.
Aggregation and publishing. Keep raw logs compressed/private; publish daily/weekly aggregate JSON and compact search indexes.

指標定義

Metric Definitions

指標初期定義注意点
Usage観測ロードアウト内でその武器が出現した割合。武器種別・枠別・モード別に集計。「装備されている」と「実際に撃った」は別。PGCRのweapon entryと装備snapshotを分ける。
Kill Share全武器キルに対する、その武器のキル割合。特殊/ヘビーは弾薬経済の影響が大きいため、Primaryと分けて見る。
K/UKill Share / Usage Share。1.00を平均、100%表記も併記可能。やまひろ先生の想定が「Kills per User」なら名称を分ける。初期UIでは定義ツールチップ必須。
Perk Delta同一武器内で、特定perkあり/なしのK/U、killShare、precision、win proxyの差分。因果ではなく相関。最低サンプル数、モード、マップ、プレイヤースキル proxyで補正。
Exotic Armor Adoptionクラス別・モード別に、観測ロードアウト内でそのエキゾ防具が採用された割合。装備snapshotの取得遅延があるため、信頼度を表示する。
PvP POTENTIAL対象HP、WP補正、精密/ボディダメージ、Optimal TTK、BS TTK、全弾精密/BSキル弾数、BS許容、耐久Tier、perk補正、sandboxVersion。バースト武器、チャージ武器、特殊条件perkは個別モデル。
MetricInitial DefinitionCaution
UsageShare of observed loadouts in which the weapon appears, grouped by weapon type, slot, and mode.Equipped and actually fired are different. Keep PGCR weapon entries separate from equipment snapshots.
Kill ShareWeapon kills divided by all observed weapon kills.Analyze primary, special, and heavy separately because ammo economy changes interpretation.
K/UKill Share / Usage Share. Show 1.00 baseline and optionally 100% format.If the intended meaning is "Kills per User", use a separate label. The first UI should include a definition tooltip.
Perk DeltaWithin the same weapon, compare K/U, kill share, precision, and win proxy between rolls with and without a perk.Correlation, not causation. Use minimum sample counts and adjust by mode, map, and skill proxy.
Exotic Armor AdoptionClass/mode-specific share of observed loadouts using a given exotic armor piece.Display confidence because equipment snapshots may be delayed.
PvP PotentialTarget HP, WP bonus, precision/body damage, Optimal TTK, BS TTK, crit/body shots to kill, body-shot forgiveness, resilience tier, perk modifiers, sandbox version.Burst, charge, and conditional-perk weapons require custom models.

英語/日本語切替設計

Bilingual Design

DB側

Database Layer

hashやactivityIdなど言語非依存IDを主キーにし、表示文字列だけ entity_i18n に分離します。Bungie Manifestは言語別ファイルを持つため、en と ja を同時に取り込みます。

Use language-independent IDs such as hashes and activity IDs as primary keys. Keep display strings in entity_i18n. Bungie Manifest exposes language-specific definition files, so import en and ja together.

UI側

UI Layer

URLパラメータ ?lang=ja / ?lang=en とブラウザ保存を併用します。日本語欠落時は英語にフォールバックし、管理画面では「翻訳欠落リスト」を出します。

Use ?lang=ja / ?lang=en plus local browser preference. Fall back to English when Japanese is missing, and expose a missing-translation report for maintenance.

2026年6月9日アップデートへの備え

Preparing for the June 9, 2026 Update

Bungie公式発表では、2026年6月9日に Destiny 2: Monument of Triumph が全プレイヤー向けに提供され、これがDestiny 2の最終ライブサービスコンテンツ更新になるとされています。PvPでは新モード、Iron Banner/Trialsの運用、Competitive報酬、エキゾ防具Tier 5、武器/防具更新など、DBに影響する変更が多いです。
Bungie announced that Destiny 2: Monument of Triumph launches for all players on June 9, 2026, and will be Destiny 2's final live-service content update. PvP modes, Iron Banner/Trials cadence, Competitive rewards, exotic armor Tier 5 stats, and weapon/armor updates can all affect the database.
  • Pre/Post分割: season_window または sandbox_version で、2026-06-09前後の集計を絶対に混ぜない。
  • Manifest差分: 新規/削除/再発行/名称変更/パークプール変更を差分レポート化。
  • 新モード対応: Arena、Glass Cannon、Software、SRLなどはmode taxonomyに追加できるようにする。
  • ライブ終了後: 更新頻度を「週次集計 + コミュニティ検証PvP POTENTIAL + アーカイブ保全」に落として継続可能にする。
  • Pre/post split: Never mix pre- and post-June 9 data. Partition by season_window or sandbox_version.
  • Manifest diffs: Produce reports for new, removed, reprised, renamed, and perk-pool-changed items.
  • New modes: Keep the mode taxonomy extensible for Arena, Glass Cannon, Software, SRL, and future community categories.
  • After live-service end: Reduce maintenance to weekly aggregates, community-verified PvP Potential, and archival preservation.

GitHub/Discord分担方針

GitHub/Discord Responsibility Split

GitHub

GitHub

  • 保管対象はテキストデータ、スキーマ、コード、小さなJSON/CSV/Markdownのみ
  • DATABASE: Manifest由来の英日名称、武器/パーク定義、PvP POTENTIAL表
  • BATTLE LOG: 集計済みの武器Usage、K/U、perk差分、エキゾ防具採用率
  • 画像、API Key、生ログ、個人単位データは置かない
  • Store text data, schemas, source code, and compact JSON/CSV/Markdown only
  • DATABASE: bilingual names, weapon/perk definitions, PvP Potential tables
  • BATTLE LOG: aggregated weapon usage, K/U, perk deltas, exotic armor adoption
  • No images, API keys, raw logs, or player-level data

Discord

Discord

最終大型アップデート後に新設し、交流、画像参照、装備データ参照、検証募集、更新告知の拠点にします。既に課金アカウントがある前提なので、初期はDiscordの運用資産を活かします。

Create it after the final major update as the hub for community discussion, image reference, equipment data lookup, validation requests, and update notices. Since a paid Discord account already exists, use that operational base first.

保留するもの

Deferred Choices

Cloudflare Pages/R2などの外部公開・外部画像保管は、Discord運用で不足が見えた段階で再検討します。最初から固定費や追加インフラを増やさない方針です。

External publishing and image storage such as Cloudflare Pages/R2 will be revisited only if Discord operations show a real gap. Avoid adding fixed cost or extra infrastructure at the start.

最初のMVPでは、GitHubに上げる前提のデータをテキストに絞ります。画像はDiscordで参照できる形にし、GitHub側は画像URL/Discord投稿参照/manifest icon pathなどの参照情報だけを持つ設計にします。
For the MVP, keep GitHub-bound data text-only. Images should be referenced through Discord, while GitHub stores only references such as image URLs, Discord post references, or Manifest icon paths.

パーク差分とエキゾ防具評価の設計

Perk Delta and Exotic Armor Analysis

分析方法表示方針
武器パーク差分同一武器内でperk有無を比較。モード、マップ、プラットフォーム、期間、プレイヤースキルproxyで層別化。「+8% K/U」だけでなく、サンプル数、信頼区間、取得信頼度を併記。
組み合わせパーク3列目+4列目など主要組み合わせを集計。ただし組み合わせ爆発を避け、最低サンプル数未満は非表示。roll heatmapとして表示。上位だけでなく、武器内平均との差分で見る。
エキゾ防具採用率クラス/サブクラス/モード/期間別のロードアウト採用率を計算。採用率、勝率proxy、K/D proxyは分ける。強さランキングに直結させない。
AnalysisMethodDisplay
Weapon perk deltaCompare perk-present vs perk-absent within the same weapon, stratified by mode, map, platform, period, and skill proxy.Show sample size, confidence interval, and snapshot confidence, not only "+8% K/U".
Perk combinationsAggregate major combinations such as columns 3+4. Hide combinations below minimum sample thresholds.Use roll heatmaps and compare against the weapon's own baseline.
Exotic armor adoptionCompute adoption by class, subclass, mode, and period.Keep adoption, win proxy, and K/D proxy separate. Do not present adoption as direct power ranking.
パーク差分は、強いプレイヤーが好むrollが高く出るバイアスを強く受けます。初期段階では「観測された相関」として表示し、「このperkが勝率を上げた」と断定しない運用が安全です。
Perk deltas are strongly biased by skilled players preferring certain rolls. Present them as observed correlations and avoid claiming that a perk caused higher win rate.

MVP 2: PvP Potential tables. PvP Potential schema by archetype, source evidence, sandbox version, validation status.

未確定事項

Open Decisions

  • K/Uの定義: 本計画では Kill Share / Usage Share を仮採用。やまひろ先生の意図が「Kills per User」なら別指標として設計変更します。
  • Discord設計: サーバー構成、ロール、チャンネル、画像参照ルール、AI更新フローは最終大型アップデート後に決めます。
  • 公開範囲: プレイヤー単位の生データは匿名化しても扱いが繊細です。公開は集計値のみを推奨します。
  • 取得母集団: opt-in/クラン中心ではバイアスが出ます。UIに「観測範囲」を必ず出します。
  • 画像保管: Bungieアセットは非商用ファンコンテンツとして扱い、著作権/商標の注意書きをサイトに明記します。
  • API継続性: ライブサービス終了後もAPIが同様に維持される保証は未確認です。Manifestと集計データの定期アーカイブが保険になります。
  • K/U definition: This plan assumes Kill Share / Usage Share. If the intended meaning is "Kills per User", design it as a separate metric.
  • Discord design: Server structure, roles, channels, image reference rules, and AI update flow will be decided after the final major update.
  • Publication scope: Player-level raw data remains sensitive even when anonymized. Publish aggregate values only.
  • Observed population: Opt-in and clan-based sampling creates bias. Always show sample coverage.
  • Image storage: Treat Bungie assets as non-commercial fan content and include copyright/trademark notes on the site.
  • API continuity: API behavior after the end of live-service updates is not guaranteed. Regular Manifest and aggregate archives are the hedge.
